# Results and interpretation

## Real LiveKit audio replay — 2026-09-19

**Configuration boundary:** this full paired dataset was collected before the Windows audio workaround. It used default 24 kHz room input and cloud session recording. The current worker requests 16 kHz input and disables cloud recording to avoid additional Soxr resampling after a native `FFT_LEN == -1` assertion was reported. The paired comparisons below remain internally consistent for the earlier configuration, but are not performance measurements of the revised worker. Subsequent smoke checks are reported separately and are not pooled into these statistics.

These measurements used the committed WAV recordings through LiveKit Cloud, Deepgram `nova-3`, OpenAI `gpt-4o-mini` and `gpt-4o-mini-tts` (`alloy`). The Python worker and receiver ran on the same Windows development laptop; media and provider requests used the network. This is a working cloud-connected audio pipeline, not a publicly hosted web deployment.

There are **36 recorded attempts**, including two excluded warmup runs and a documented retry pair. The original batch scheduled two repetitions of all eight scenarios, with randomized scenario and A/B order. One full pair was retried after clock setup failed before audio started. The original failure and its unmatched successful partner remain in the JSON. The final comparison uses **15 complete matched pairs**. No run was retried because of its latency.

### What became slower?

The enabled-minus-baseline median response difference is -250.7 ms; the P95 difference is +695.3 ms. Individual scenarios vary:

| Scenario | Mean paired response delta |
| --- | ---: |
| long_monologue | +1,005.4 ms |
| stop_at_decision | +763.9 ms |
| short_answer | -664.7 ms |
| multiple_backchannels | +1,674.6 ms |
| noisy_audio | -74.5 ms |
| approaching_eot | +209.0 ms |
| fast_speaker | -1,143.9 ms |
| mid_sentence_pause | +290.1 ms |

This experiment does not establish that acknowledgements cause or avoid a slowdown. Provider timing, text generated by the LLM, network jitter, and shared-laptop load vary between paired sessions. The independent audio path avoids intentionally queuing a response behind an acknowledgement, but cannot guarantee constant latency. LLM/TTS stages are diagnostics from the last completed correlated request before response audio, not an additive decomposition or proof of causality.

### Behaviour and limitations

- Short-answer suppression and long-turn acknowledgements can be inspected in the paired timelines. Real noisy speech may still produce sufficiently confident transcripts and acknowledgements; the simulation deliberately supplies low confidence instead. These are different tests.
- Near-EOT acknowledgements remain a failure mode of heuristic gating. Cancellation cannot retract PCM already transmitted or buffered by a receiver. Do not interpret zero response overlap as proof that all acknowledgements were well timed.
- The fixed VAD endpointing can split a fixture at sentence pauses and start cancelled generations. All turn-end and node events remain visible. Request IDs prevent unrelated node attempts from being subtracted in stage metrics.
- Clock-alignment uncertainty ranged from 44.9 to 64.2 ms across successful attempts. That uncertainty affects worker-to-receiver backchannel timing; response onset and source speech end share the receiver clock. Physical speaker latency is not measured.
- This was a shared development laptop with brief test and browser activity, not an isolated performance host. Input scheduling drift is recorded and runs above 50 ms are invalidated, but this does not eliminate resource-contention confounders.
- Speech is synthetic and the acknowledgement clip is fixed. No blinded human listening study was performed, so increased conversational naturalness remains unproven.

### Retained failures

Both arms of the retry pair timed out waiting for worker readiness. The local worker was absent when inspected and was restarted afterward. These failures remain excluded; no additional retries were performed. The pause scenario consequently has only one complete pair, so its within-scenario uncertainty cannot be estimated and the overall confidence interval is withheld. A false regression flag here means insufficient evidence, not evidence of no regression.

## Controlled engine simulation

The separate `simulation.json` has 40 complete pairs (80 runs): response P50 898.8 ms and P95 926.2 ms in both modes, 65 simulated acknowledgements, backchannel P50 120 ms, 10 cancellations, five near-EOT collisions and no response overlap.

The simulated response schedule is identical by construction in each pair. Zero delta is **not** evidence of real-world equivalence. It tests repeatable policy behaviour, including a pending acknowledgement cancelled by abrupt stop and late acknowledgements in the pause scenario. Keep these results separate from the live measurements above.
