LISTENING IS AN ACTIVE PROCESS
THE ENGINEERING ARGUMENT

Acknowledge the speaker. Protect the answer.

A listening sound is useful only if it does not take over the conversation.

The assignment asks whether an agent can feel more attentive without damaging turn-taking or delaying its real response. This project treats that as a measurable hypothesis, not a feature claim. The design gives normal answers priority and makes every acknowledgement disposable.

Engineering decisions come first: a small independent engine, bounded asynchronous work, repeatable audio inputs, and visible failure cases.

LISTENING ACKNOWLEDGEMENT

Public events → policy → cached audio

A separate cancellable task publishes “mm-hmm” on its own track. It does not call session.say(), add chat history, or join the normal response queue.

User stops, end-of-turn risk rises, or a normal answer starts → cancel the acknowledgement and clear its outgoing queue.

Why these choices?

Each decision removes one risk and leaves an explicit trade-off.

DecisionReasonTrade-off
Cached acknowledgementNo network TTS request on the listening path; predictable preparation time.Less voice variety and no semantic personalization. Slow and failed providers are still tested through the engine’s provider interface.
One active taskA 20 Hz policy loop cannot create a new audio task for every transcript event.An opportunity can be skipped while a task is pending. Skipping is preferable to a queue of stale acknowledgements.
Conservative eligibilityRequire 2.4 seconds of continuous speech, at least five recent words, and an idle answer path.Pauses reset the speech window. Some appropriate acknowledgements will be missed.
Cooldown and turn budgetWait 4.5 seconds between attempts and allow at most three started acknowledgements per detected turn.A recording may contain multiple detected turns, so its total can exceed three.
Heuristic end-of-turn riskPunctuation and low transcript confidence provide a cheap, inspectable suppression signal.This is not a calibrated probability or a semantic turn detector. It cannot reliably recognize an unfinished thought such as “Okay. And”.
Public LiveKit APIsUse documented agent hooks, state events and RTC audio methods; keep the engine independent of the SDK.The engine cannot retract audio already delivered to a receiver or control provider and network delay.

Policy details: transcripts expire after 2 seconds; confidence below 0.6 suppresses acknowledgement; risk at or above 0.55 cancels; preparation cancellation is requested after 650 ms. These are initial engineering choices, not thresholds optimized on a human evaluation set.

    What counts as a bad acknowledgement?

    Behaviour worth counting

    An acknowledgement starting in the final 400 ms of the annotated user turn, or later, is flagged as near-end. Overlap with an answer is undesirable. Speaking over the user is expected for a listening sound, so the duration is reported rather than automatically called a failure.

    A positive paired response delta is a warning to investigate. It does not identify a particular acknowledgement as the cause of delay.

    What I would change next

    Evaluate a semantic turn detector on held-out human recordings, calibrate the suppression threshold, and compare naturalness with blinded listeners. Collect more paired repetitions on an isolated host before making tail-latency claims.

    The Windows workaround now uses 16 kHz input and disables extra cloud recording. The full stored benchmark predates that configuration; four subsequent real-audio smoke checks passed, but a fresh full benchmark is still needed for the final worker.

    How the approach is tested against the assignment

    The automated suite covers all nine required behaviours: short and long speech, cooldown, stop-before-playback, approaching turn end, answer priority, slow/failed TTS, rapid speech/silence transitions, and shutdown.

    Additional checks cover duplicate event storms, stale transcripts, a provider that ignores cancellation, public adapter hooks, audio forwarding, matching audio hashes, and incomplete statistical pairs. These checks establish specific invariants, not perfect conversational quality.

    The generation counter is checked after preparation returns, so an old task cannot resume playback after cancellation. The task limit bounds work and the cooldown bounds retries. Async cancellation is cooperative: a provider that never yields or never returns can still stall work or shutdown. Production providers need their own network deadlines; blocking code needs isolation. Late audio returned after an expired timeout is rejected. The normal answer path never awaits an acknowledgement.
